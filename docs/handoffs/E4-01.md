### Design discrepancies — screen 06, iOS (`design/stitch/ios-liquid-glass/screens/06-settings.md`)

Recorded per `docs/DESIGN.md §7`; none is implemented.

1. Presented as a sheet with a "Cerrar" action. Implemented as a pushed screen with the system back
   button (`A-4`).
2. Chevrons on the read-only distance and volume units (correction 5). Implemented as static text with
   no chevron and no action (`§3.1`).
3. Currency shown as "EUR €". Implemented as the platform display name plus the code ("Euro (EUR)"),
   because `SettingsUiState` carries only the code and the host names it through the platform.
4. Backup row with the subtitle "Última sincronización local guardada" and an "Activa" chip, which
   claim a remote copy (`D-193`) and offer no retry. Implemented as the `E3-05` indicator with the
   `D-193` labels and the retry on `Failed`.

   pseudonymous; the copy says "seudonimizados" / "pseudonymous".
6. "CUENTA" always shows "Cerrar sesión" and "Eliminar cuenta". `B1-D5`: local and anonymous owners see
   one "Eliminar datos locales" row and no sign-out.
7. Footer tagline "Local-First & Safe Tracker": extra copy that `§3.1` does not list. Omitted.
8. Footer "carApp v1.0.0" while the app ships `0.0.1` build `1`. Implemented as a "Versión" row reading
   the bundle (`B1-D2`).
9. The pending-sync prompt, the destructive confirmations, the departure progress, the failure with
   retry and the re-authentication stage are undrawn (`docs/DESIGN.md §6`, "Not every state is
   designed"). They use system alerts and a system-styled screen.
10. The Liquid Glass backdrop, the teal accent and the vermilion destructive label are not applied; the

## Design Discrepancies (screen 06, Android)

The design is non-normative (`docs/DESIGN.md §7`). None of the contradictions below was implemented;
the normative source decided instead. Line numbers refer to
`design/stitch/android-m3-expressive/screens/06-settings.md`.

1. **Chevrons on the read-only units** (lines 16-17, 37). "Unidad de distancia → Kilómetros" and
   "Unidad de volumen → Litros" carry a chevron, which signals navigation or editing.
   `docs/SPECIFICATION.md §3.1` makes `distanceUnit` and `volumeUnit` visible and read-only in the
   MVP. Implemented as rows with no chevron and no click action
   (`SettingsScreenTest.theUnitRowsAreVisibleAndOfferNoClickAction`).
2. **A backup subtitle and an "Activa" chip that claim a remote copy, and no retry** (lines 19-20,
   38). "Última sincronización local guardada" and "Activa" describe a recorded, active backup.
   `D-193` and `docs/CONTRACTS.md §9.9` make `Idle` mean only that nothing is outstanding, `§9.1`
   enqueues nothing while the owner is `LOCAL_OWNER`, and `docs/SPECIFICATION.md §3.1` requires a
   backup status indicator with manual retry. Implemented by reusing the `E3-05`
   `SyncStatusIndicator` and its classifier, with Retry on `Failed` only.
3. **"Comparte telemetría anónima…"** (line 23). `docs/CONTRACTS.md §16.1` and `D-203` (ADR-0204)
   state that the measurement is pseudonymous, not anonymous. The copy
   (`settings_analytics_description`) says pseudonymous in both languages.
4. **No "delete local data" row for local and anonymous owners** (lines 25-27, 40). The design shows
   "Cerrar sesión" and "Eliminar cuenta" to every owner. `docs/CONTRACTS.md §11.5`, `§20.10` and
   `docs/SPECIFICATION.md §7 F-5` offer sign-out only to a permanent session and label the anonymous
   action "delete local data". Implemented per B1-D5: `PERMANENT` shows "Sign out" and "Delete
   account"; `LOCAL` and `ANONYMOUS` show one "Delete local data" row.
5. **A tagline that is extra copy** (lines 29, 41). "Local-First & Safe Tracker" is untranslated copy
   outside the `§3.1` surface and outside the localization catalogue. Not implemented.
6. **"carApp v1.0.0" while the host ships `0.0.1`** (lines 29, 41; `androidApp/build.gradle.kts:10`).
   The version row reads the installed package's `versionName` (B1-D2), so it shows `0.0.1`.

Presentation differences that contradict nothing normative, recorded for the `E4-02` audit: Back is
the existing host `TextButton`, not an arrow icon; the currency value is the platform display name
plus the ISO code ("Euro (EUR)"), not "EUR €"; the Material default colour scheme is used and the
design palette, rounded cards and full-width dividers are not applied (no story owns theming,
B1-D13); the pending-sync prompt, the destructive confirmations, the departure screen and its
re-authentication choice are undesigned (`docs/DESIGN.md §6`) and derive from Material 3 components.

build of the `story/E4-B1-product-surface` head under review (record the commit SHA;

Re-authentication timing: `deleteAccount()` asks for re-authentication when the cached ID token is
older than 5 minutes. Run the "fresh" case within 5 minutes of signing in, and the "stale" cases
between 6 and 50 minutes after signing in (the SDK refreshes an expired token after about an hour,
and a refreshed token counts as fresh, F-A3).

  vehicle. Settings → Sign out. Expected: the "Changes not backed up yet" dialog states "1 change has

  the vehicle is still listed. Turn airplane mode off and wait until the backup status reads "Synced
  locally". Settings → Sign out. Expected: no dialog; a short departure screen; the welcome screen.

  Settings → Sign out → "Cancel". Expected: still signed in, data unchanged, Sign out can be

  continue". Expected: departure screen, then the welcome screen. Turn airplane mode off, sign in with

  Expected: no confirmation (`docs/CONTRACTS.md §20.10`), then the welcome screen.

- **M7 — Stale login, cancel on the departure surface.** As M6 up to "Sign in again", then tap
  "Cancel". Expected: back on the vehicle list, no error, still signed in, data present. Settings →

## Risks or Follow-ups

- The six `SettingsGraphTest` graph tests wait in real time (`D-204`), so they cost wall-clock
  time and depend on real CPU like the other graph tests; their budget is
  `GRAPH_STATE_EXPECTATION_TIMEOUT`.
- Pre-existing, unchanged: every first subscriber of the settings flow that observes the missing
  row upserts the defaults (`SqlDelightSettingsRepository.kt:46-55`, `ON CONFLICT DO UPDATE`). A
  default upsert that started before a user write and committed after it would overwrite that
  write. The tests wait for both the holder and the opt-in gate to load before writing, and in
  production the screen opens long after start-up, so the window is not reachable in practice.
- `E4-02` (`D-221`) must allowlist `SettingsUiState.currencyCode` and
  `SettingsUiState.supportedCurrencyCodes` in its `UiState` `String` rule, and its host mapping
  rule must cover `VALIDATION.INVALID_UNIT`, `PERSISTENCE.DATABASE_UNAVAILABLE` and
  `PERSISTENCE.TRANSACTION_FAILED`, which this holder publishes.
- **F-A1 — residual risk (shared, pre-existing): a permanent deletion whose durable marker cannot be
  written stays in `DELETING` with no retry until relaunch.** If writing the `D-166` departure marker
  fails before the `D-23` call (`AccountDepartureFlow.kt:437-442`), `failDeparture`
  (`AccountDepartureFlow.kt:631-643`) keeps the phase `DELETING` and publishes the error, but
  `pendingDepartureRetry` is `null` because the remote step is still owed
  (`AccountDepartureFlow.kt:79-99`), and the retained request blocks a new `requestDeleteAccount()`.
  The Android departure screen shows the typed error and offers no action
  (`DepartureScreenTest.aFailureWithoutARetainedStepOffersNoRetry`). Relaunching the app recovers (a
  new holder; nothing was deleted, and the next launch finds no marker to resume). Low probability: a
  local SQLite write failure. Recorded as a residual risk, with no mechanism added in `E4-01`.
- **F-A2 (shared, pre-existing): a failed re-authentication leaves no typed state to retry it.**
  When `AuthClient.reauthenticate()` fails after a successful picker, the request is kept awaiting
  re-authentication (`StateHolders.kt:460-471`) and the error is published without any
  `confirmation`, so the session is no longer busy, the host flag turns off and the owner returns to
  the vehicle list with an `ERROR` dialog. Once it is dismissed, `SessionUiState` no longer shows that
  re-authentication is pending, and `requestDeleteAccount()` and `requestSignOut()` return silently
  while the request is retained. Relaunching the app recovers. Low probability: the picker succeeded
  but the provider then refused the credential. (A cancelled or failed picker is not affected: it
  goes through `failSignIn`, which abandons the request.)
- **F-A3 (observation, not verified on a device): freshness is measured on the ID token's
  `issuedAt`.** `FirebaseAuthClient.kt:181-193` compares the cached token's `issuedAt` with
  `FRESH_LOGIN_THRESHOLD_MS`. A token the SDK refreshed on its own has a new `issuedAt`, so a deletion
  shortly after an automatic refresh may not ask for re-authentication. For `E4-04` or a security
  review; no change in `E4-01`.
- **F-A4 (observation): sign-out keeps the phase `PERMANENT` while it runs.** §20.10 (line 3148-3149)
  says "While a departure is running the phase is `DELETING`", but `confirmSignOut` and an
  empty-outbox sign-out resume with `phase = null` (`AccountDepartureFlow.kt:168-172,405-412`). The
  Android host shows sign-out progress in Settings and switches to the departure screen at the
  `UNKNOWN` hand-over; it works for both readings. Report the wording gap to the owner.
- **Copy for E4-02 (B1-D9):** a departure that fails offline reuses `error_auth_network` ("Sign-in
  needs a network connection…"), whose wording names sign-in.
- **Settings needs a vehicle on Android:** the entry point is on the vehicle list, and F-1 makes a
  first vehicle mandatory, so an owner without vehicles reaches "Delete local data" only after
  creating one.


- **Unretryable marker failure (shared, pre-existing).** A permanent deletion whose durable departure
  marker cannot be written publishes `DELETING` with a typed error and no retry, while the request is
  retained (`AccountDepartureFlow.kt:79-99`, `:631-643`). The departure screen shows the error and an
  OK; after it the screen shows progress until relaunch, where the account and the data are intact
  (`D-167` drops a deletion whose `D-23` call never recorded success). Candidate for `E5-02`/`E5-04`.
- **Failure alert over mandatory first-vehicle creation.** After a failed permanent deletion the
  signed-in surface is mounted again; for a permanent owner with no vehicle, F-1 presents the mandatory
  first-vehicle sheet, and the failure alert attached to the root may not present over it. Owners
  reach Settings only from the list, which needs a vehicle, so this needs a vehicle deleted after its
  creation. Checked by checklist item IOS-M11.
- **Network copy on a deletion failure.** `AUTH.NETWORK_UNAVAILABLE` reads "Sign-in needs a network
  connection" for a deletion attempted offline. `E4-02` (`B1-D9`) owns per-outcome copy.
- **Apple token revocation** (an `E4-04` intake question) is not part of `E4-01`. `E4-04` captures the Apple
  `authorizationCode` in the deletion's re-authentication, which now runs through
  `NativeSignInCoordinator.prepareAppleReauthenticationRequest` / `completeAppleAuthorization`.
- **CI runs the Settings flows as a `LOCAL` owner** (no App Check debug token), whose outbox is always

  with a token or by IOS-M10.

`rememberGoogleSignIn` (`onNativeAcquisitionAbandoned`, which clears the stage only when a native
acquisition ends without a credential). `SessionErrorText` now announces the typed failure
(`announcedError()`).
