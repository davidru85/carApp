## Decisions Made

- `D-211` (ADR-0212): `SettingsStateHolder` lives in `:shared`.
- `D-212` (ADR-0213): each host reads its own app version natively.
- `D-213` (ADR-0214): "wait" withdraws the sign-out prompt and requests a `PullToRefresh` cycle.
- `D-214` (ADR-0215): a root-level host departure screen renders progress, failure and retry.
- `D-215` (ADR-0216): `PERMANENT` shows sign-out and account deletion; `LOCAL` and `ANONYMOUS` show
  one local-data deletion row.
- Design 06 contradicts the normative documents in six places, none of which is implemented
  (`docs/DESIGN.md §7`: the normative document wins): chevrons on the read-only units; a backup
  subtitle and an "Activa" chip that claim a remote copy (`D-193`) and offer no retry; "telemetría
  anónima", where `D-203` and `docs/CONTRACTS.md §16.1` say pseudonymous; no "delete local data" row
  for local and anonymous owners; a tagline that is extra copy; "v1.0.0" while both hosts ship
  `0.0.1`.
- Shared code used no TDD exemption: every shared behaviour was committed failing first
  (`66cb982e`), then made to pass (`69f49134`), then refactored (`6bd37640`).
- Deviation, recorded per rule G-7 of the bundle process: the RED test scaffold of
  `SettingsStateHolderTest` was defective and was corrected inside the GREEN commit
  (`69f49134`), not by a spec revision. The `collectedHolder` helper built the holder with
  `dispatchers = TestDispatcherProvider(StandardTestDispatcher(testScheduler))` while the holder's
  scope was `backgroundScope`. `backgroundScope` marks its work as background
  (`kotlinx-coroutines-test` `TestScope.kt`: `coroutineContext + BackgroundWork + …`), and
  `TestCoroutineScheduler.advanceUntilIdle()` returns as soon as only background events remain
  (`TestCoroutineScheduler.kt:110`), so no holder coroutine ever ran and all 17 assertions failed
  regardless of the implementation. The helper now uses `UnconfinedTestDispatcher(testScheduler)`.
  No test name, assertion or production signature changed, and the RED semantics remain valid: with
  the stub restored and the corrected scaffold, `SettingsStateHolderTest` fails 17 of 17 by assertion.
  `SettingsGraphTest` drives real-time waits instead of the virtual scheduler, so it was unaffected.
- `SettingsStateHolder` follows `§14` literally (`stateIn` on `main` under `WhileSubscribed`,
  repository on `io`) rather than the `MutableStateFlow` shape of `SyncStateHolder`, which `§14`
  does not exempt.
- The holder semantics written into `docs/CONTRACTS.md §20.10` under `D-211` follow existing
  patterns and took no new owner option, so no new decision ID: the saving guard of
  `FuelEntryFormStateHolder.save()`, the typed read-error relay of the list holders, no optimistic
  update, and message ids 8 (read failure) and 9 (failed write or rejected currency) continuing
  the `:shared` sequence that ends at 7.
- `SwiftAppGraph.settingsStateHolder()` sits before `syncStateHolder()` in the class and in
  `§20.10`, because `Pr71ReviewRegressionTest` anchors on `syncStateHolder()` being the last
  factory before `close()`.
- The graph tests use the bounded real-time waits of `D-204` instead of the `E3-09` test seams;
  `awaitGraphEffect` is the single implementation of that pulse after the REFACTOR phase.
- Rule 0 held for this part.

## Risks or Follow-ups

- The four `SettingsGraphTest` graph tests wait in real time (`D-204`), so they cost wall-clock
  time and depend on real CPU like the other graph tests; their budget is
  `GRAPH_STATE_EXPECTATION_TIMEOUT`.
- Pre-existing, unchanged: every first subscriber of the settings flow that observes the missing
  row upserts the defaults (`SqlDelightSettingsRepository.kt:46-55`, `ON CONFLICT DO UPDATE`). A
  default upsert that started before a user write and committed after it would overwrite that
  write. The tests wait for both the holder and the opt-in gate to load before writing, and in
  production the screen opens long after start-up, so the window is not reachable in practice.
- `E4-02` (`D-221`) must allowlist `SettingsUiState.currencyCode` and
  `SettingsUiState.supportedCurrencyCodes` in its `UiState` `String` rule, and its host mapping
  rule must cover `VALIDATION.INVALID_UNIT`, `PERSISTENCE.DATABASE_UNAVAILABLE` and
  `PERSISTENCE.TRANSACTION_FAILED`, which this holder publishes.
