## Decisions Made

- `D-207` (ADR-0208), decided before the story started.
- The reset reaches the controller as a `staleSyncingReset` function parameter, like `adoption`,
  rather than as an eleventh `SyncPersistence` member: detekt's `TooManyFunctions` rejected the
  eleventh member, and suppression was not used. An implementation detail inside `D-207`'s placement,
  with no behavioural alternative.
- TDD notes (`SHOULD` deviations, declared): the first RED included a no-op `resetStaleSyncing()`
  skeleton so the tests compiled and failed on behaviour, and the controller RED included the
  `staleSyncingReset` parameter and its `createSyncController` wiring for the same reason.
  `theResetLeavesTheOutboxRetryContextUnchanged` and the two `aResetWithWorkToDoStillResetsTheRow`
  tests are constraint tests that passed before the code they guard; `StaleSyncingResetAppGraphTest` is
  an acceptance test written after the wiring, proved non-vacuous by mutation.

## Risks or Follow-ups

- A launch with no host foreground report and no owner transition (for example a background-only
  periodic worker start) still resets at its first cycle, which is the periodic one; a process that
  runs no cycle at all leaves the stale rows until the next cycle, exactly the pre-story behaviour.
- After a restart, a row whose last resolved attempt failed for a non-connectivity reason now shows
  `Failed` with the retry control instead of `Pending`; this is the intended, honest signal of `D-207`.
