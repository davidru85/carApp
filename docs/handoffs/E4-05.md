## Decisions Made

- `D-224` (ADR-0225): the account-link row is hidden while the session is `LOCAL`.
- The row and collision-confirmation design was approved by the owner on 2026-10-16 and is
  recorded in both `design/stitch/*/screens/06-settings.md` files (non-normative, no decision ID).
- TDD order exemption (`docs/SPECIFICATION.md §11`, "Native UI code (SwiftUI, Compose host
  screens)"): every change of `E4-05` is host code — the Compose and SwiftUI conversion surface, its
  pure host visibility and message-selection helpers, the host string mappings and the native
  sign-in coordinator entry. No shared behaviour was added: row visibility is derived on each host
  from `SessionUiState.phase`, and the conversion behaviour itself is `E2-04`'s, covered by
  `SessionStateHolderTest` and `AccountConversionCoordinatorTest`. The tests were written with the
  code rather than first, and each new test was then proven to fail against a deliberate reversal
  of the behaviour it asserts. This is a declared SHOULD deviation; no MUST is waived.
- `D-227` (ADR-0228): a displayed credential collision is cancelled with `clearMessage()`, now
  stated in `docs/CONTRACTS.md §20.10` (`E405-Q1`, option A, 2026-10-16; the `UidWouldChange`
  correction was applied). A cancelled native picker stays
  `failSignIn(NativeSignInFailure.CANCELLED)`.
- `D-228` (ADR-0229): the two `E2-04` interruption hazards are accepted residual risks in
  `docs/SECURITY.md`, fixed by `E2-10` (`E405-Q2`, option A, 2026-10-16).
- The conversion intent was added to the intent split `E4-01` built in both native coordinators
  (`GoogleSignInIntent.CONVERSION`, `NativeSignInIntent.conversion`); no second picker path exists.
- Conversion errors are presented by the session-error presentation `E4-01` built (on iOS the
  `DeparturePromptPresenter`), pointed at the session-channel copy; the collision confirmation is
  presented only by the `E4-05` dialog and alert, so nothing is presented twice.
- The host renders no conversion-progress state of its own: after the session switch
  `SessionUiState` reports `PERMANENT` with `isBusy = false` while the replacement continues, and a
  pending replacement has no typed state. The vehicle list's existing waiting indicator covers the
  resume, and a `REMOTE.*` failure on the session channel reads as a replacement that carApp keeps
  retrying.
- The row's progress indicator follows `SessionUiState.isBusy`, which the outbox count of a
  local-data deletion also raises for a moment; the row shows the indicator for that interval too.
- Rule 0 held for the whole story: every chat reply was in Spanish (es-ES) and every repository
  artifact is in technical English. No violation occurred.

collision dialog was mounted only inside `SettingsScreen`, and the root presenter classified
`Confirmation.AdoptExistingAccount` as `SessionPrompt.NONE`, so a collision arriving after Settings
unmounted had no visible confirmation until Settings was reopened.

`AdoptExistingAccount` to it; `SessionPromptCallbacks` gains `onConfirmAccountConversion` and
`onCancelAccountConversion`; `sessionPromptCallbacks` binds them to
`confirmAccountConversion(Confirmation.AdoptExistingAccount)` and `clearMessage()`; and
`SettingsSessionPrompts` renders `AccountConversionCollisionDialog` for the new case. The former
`SettingsScreen` invocation and the two `SettingsCallbacks` members were removed, so the root presenter
is the single owner of the collision.
