## Review Correction R1 (pull request #88)

The owner review found that the iOS `untypedFields()` actual and its recursive map branch coerced
every map key with `(key as? String ?: key?.toString().orEmpty())`. A numeric key became text and a
null key became the empty string, so two distinct keys such as `1L` and `"1"` collapsed into one JSON
field name and `FirebaseRemoteSyncSource.toJsonElement()` never saw the unsupported original shape.
The `D-208` marker was absent and the quarantine payload lost the representation `§9.5` requires.
`docs/CONTRACTS.md:630` and ADR-0209 make the rule independent of the map's position, so no iOS
exception exists; this correction applies the existing accepted decision and introduces no new
product policy and no new decision ID.

- The map-key rule now lives in production code the common tests execute:
  `integration/firebase-firestore/src/commonMain/.../ProviderFieldMaps.kt` owns
  `Map<*, *>.toProviderFieldMap()`, which returns one
  `{UNSUPPORTED_PROVIDER_VALUE_KEY: NON_STRING_KEY_MAP}` marker before converting any value when a key
  is not a `String`, and otherwise converts every value under its unchanged string key.
- The iOS root accessor and the recursive map branch in `UntypedFields.ios.kt` both call one private
  `Map<*, *>.toIosFieldMap()`. It renders a key only when it is a native `NSString` and passes any
  other key through unchanged, so the common rule can reject it. The list branch still recurses
  through `toJsonFriendly()` and therefore reaches the same function for a nested map.
- `ProviderFieldMapsTest` (new, commonTest) covers a numeric key, a null key, two keys that would
  collide after coercion, a key whose `toString()` throws (asserted never to be called), a valid
  string-keyed map whose values are converted, and an empty map.
- `FirebaseRemoteSyncSourcePullTotalityTest.aMapNormalizedBeforeThePullBoundaryRetainsItsMarker`
  feeds a normalized map through the production `pullChanges()` boundary and asserts the marker
  survives as `json["brand"]`.
- Test targets: the new helper suite and the new pull-boundary test execute on the Android host / JVM
  through `:integration:firebase-firestore:testAndroidHostTest`; the marker-detection and engine tests
  run on JVM and Kotlin/Native; the module's two iOS targets compile
  (`compileKotlinIosSimulatorArm64`, `compileKotlinIosArm64`). No common test directly exercised
  `FIRDocumentSnapshot.data()`, and the standalone Firebase Native test task did not run; the
  provider-integration TDD exemption and the `D-75` exclusions are unchanged.

## Review Correction R2 (pull request #88) — non-finite provider numbers

The second owner review found that the common `Any?.toJsonElement()` `is Double` branch passed every
`Double` straight to `JsonPrimitive`. Cloud Firestore supports `NaN`, positive infinity and negative
infinity as floating-point values, and JSON's number grammar excludes all three (RFC 8259 §6), so those
three values reached `rawJson` as the literal tokens `NaN`, `Infinity` and `-Infinity`. The `D-208`
representation guarantee of `docs/CONTRACTS.md §9.5` was therefore incomplete at the boundary `E3-20`
owns: the value did not become the reserved marker, and the carried payload was not valid JSON, even
though the pinned parser accepts the non-standard tokens. Both platform adapters reach that branch —
Android passes a `Double` through, iOS converts a floating-point `NSNumber` through `doubleValue` — so
the fix belongs in the common conversion. This is a closure gap, not a reachable pull stall or a
data-loss incident: the engine can still reject such a value as `MalformedPayload`.

- `Any?.toJsonElement()` now sends a `Double` to `JsonPrimitive` only when `isFinite()`; otherwise the
  existing `unsupportedProviderValue(...)` marker is emitted in that position. The marker key, the
  marker shape, the type-name fallback, the public API and the engine's classification policy are
  unchanged, so this applies `D-208` literally and introduces no new decision ID.
- The `toRawJson()` KDoc now names the finite-only numeric set.
- Transport tests in `FirebaseRemoteSyncSourcePullTotalityTest`: a root `NaN`, positive infinity and
  negative infinity each become `{"__unsupportedProviderValue":"Double"}`; the same holds for a value
  nested in a map and in a list, with the neighbouring fields, keys and list positions unchanged; and
  the finite numbers `-1.5`, `0.0`, `1.25`, `Double.MAX_VALUE` plus the strings `"NaN"`, `"Infinity"`
  and `"-Infinity"` stay verbatim.
- Acceptance tests in `FirebaseRemoteSyncSourcePullTotalityEndToEndTest`: one shared body now serves
  the unrepresentable provider value and the three non-finite numbers. It asserts the cycle succeeds,
  the real database commits a `MalformedPayload` quarantine record, the vehicle cursor advances, no
  error is reported, and the record the production persistence path wrote carries the reserved marker
  at the original position (`brand`). RED `e3bc0866` failed the four transport cases with the observed
  outputs `NaN`, `Infinity`, `-Infinity` and a nested `NaN`; GREEN `dd8e8712` made them pass.

Non-vacuity: with the finite-only branch temporarily replaced by the previous unconditional
`JsonPrimitive(this)`, all three numeric end-to-end cases failed on the missing quarantine record
(`the document is quarantined as MalformedPayload. Saw [… quarantine type=FUEL_ENTRY …]` — only the
fuel-entry collection is quarantined, because the gateway seam feeds the same unnormalized document to
both queries). The branch was restored immediately and the focused command passes again; the mutation
was never committed.
