## Out of Scope / Not Done

  `firebaseAppProviders` leave `onProviderError` at its no-op default, so a dropped metric is

  not have; recorded as a risk rather than silently left.

  session (`UNKNOWN` then signed in) emits neither onboarding event. The rule is stated in
  `SessionStateHolder.trackOnboarding`.

## Decisions Made

- `D-196` / ADR-0196 — the owner chose that `E3-09` owns the complete `§16.1` surface rather than the
  integration alone. `§16.1` attributes the cadence fixture to this story by name and seven leaves
  had no emitter, so a mapper-only story would have left a named obligation unfulfilled. The story is
  resized to `M`.
- `D-197` / ADR-0197 — the count buckets come from the owner's active rows in `:core:database`
  through two read-only, owner-scoped, `deleted = 0` queries.
- `D-198` / ADR-0198 — `snake_case` event and parameter names, enum parameters as the enum `name`,
  and originally `is_full_tank`/`had_notes` as Boolean wire values. `D-201` partially supersedes
  that wire choice: GitLive conversion accepting Boolean did not establish native Firebase support.
  Domain flags remain Boolean; the provider now receives 0L/1L.
- `D-198` / ADR-0198 — a provider failure is classified into the closed `AnalyticsProviderError` and
  handed to an injected sink; `CancellationException` is rethrown. `§16.1` declares three
  non-suspending `Unit` methods, so propagation would be an unhandled exception on a product path.
- `D-199` / ADR-0199 — the tracker is injectable into `firebaseAppProviders`, which is what makes the
  single-construction-site criterion assertable without a runtime.
- `SHOULD` deviations: the TDD order exemption of `docs/SPECIFICATION.md §11` for "Koin wiring and
  provider integration code (Firebase, GitLive)" was used for the `:wiring:firebase` binding and the
  GitLive gateway, whose tests were written against the interface first and the binding second.
- A SQLDelight query cannot be moved between commits by itself, so the two new queries ship with
  their RED commit: the test cannot reference generated code that does not exist, and the SQL is
  declarative data rather than the behaviour under test.
- `SyncStatus -> SyncStatusCategory` is total with no connectivity parameter, because `§9.9` applies
  the connectivity qualification once, where the aggregate is derived. A second observation at the
  mapping site would be the second implementation of the aggregate that `§14`, `D-192` and `D-193`
  forbid. Recorded in `SyncStatusCategoryMapping` and its test.

- Review correction round 1 (PR #84): `D-199` moved from the shared ADR-0198 to its own ADR-0199,

## Risks or Follow-ups

- The provider-failure sink is not wired in production (see "Out of Scope / Not Done").
- `docs/adr/0076` now lists `:integration:firebase-analytics`; whether the analytics provider path
  enabled event/property calls need Native-side iOS coverage stays an owner review item.
  UI app construction already reaches the collection-disabled setter; ADR-0076 now states that
  precise compensating coverage rather than claiming no Analytics SDK call at all.
- No graph test drives the real settings repository into the opt-in gate end to end: every opted-in
  graph fixture substitutes the settings flow through `settingsOverrideForTest`, because the real
  repository's notifications cross a dispatcher the virtual test scheduler cannot drain. The opt-in
  semantics are covered by `SharedAnalyticsCadenceTest` over `AnalyticsEmissions`, and the opt-out
  product path by `SharedAnalyticsEmissionTest.aDisabledTrackerRecordsNothingEvenThoughWritesSucceed`.
- `AnalyticsEmissions` keeps a non-authoritative opt-in mirror only to skip the bucket count while
  collection is off; the tracker stays the only gate, so the mirror can save a read but never let a
  payload through.
- A fresh install's onboarding precedes any opt-in, which `§16.1` places in Settings, so the
  onboarding pair is normally dropped on a fresh install by design.
- The three review choices were closed on 2026-10-14 as D-201, D-202 and D-203; their implementation
  and verification are tracked by the current checkpoint above.
- `contractCheck` assertion 23 ("no decision ID is duplicated inside a single table") reads each table
  line as one row and takes only its first cell as the ID (`DecisionRegistry.duplicatedIds`). It
  therefore missed the `D-194` row that commit `15b5bd50` glued onto a single line, which the
  2026-10-13 merge repaired. Hardening the parser to reject a line holding more than one decision
  row is a candidate follow-up for the owner. It is not part of this story.
