### 1.3 Defects found

**D-1. The iOS Release configuration bundles a development plist under the production name (latent
`D-238` defect, blocks `E4-10`).** `iosApp/Config/Staging/GoogleService-Info.plist` is byte-identical to
the development plist but carries the production file name. It is a resource of every configuration of
the `carApp` target (`project.pbxproj` lines 450-451), and `EXCLUDED_SOURCE_FILE_NAMES` matches file
names: Staging excludes `GoogleService-Info.plist` (so it bundles only the debug plist), but Release
excludes only `GoogleService-Info-Debug.plist`, so today a Release bundle would contain the development
configuration as `GoogleService-Info.plist`, which `firebaseConfigurationResourceName` loads for Release.
No artifact exists today only because the `D-238` pre-build script fails first (empty
`GOOGLE_REVERSED_CLIENT_ID`, then the missing `Config/Release/GoogleService-Info.plist`). When `E4-10`
supplies both, either the production plist is added as a resource and the two same-named resources
collide (Debug and Release fail with a duplicate-output error), or it is not added, the script still
passes because it checks the file on disk, and Release ships the **development** configuration. The
guard only checks that the string `EXCLUDED_SOURCE_FILE_NAMES: GoogleService-Info-Debug.plist` appears.
`D-238` states that changing the selection mechanism or moving a configuration file needs a superseding
decision. Recommended fix and decision: §3.3 and W-37. **Resolved** in the review round 1 of pull
request #94 by `D-261` (ADR-0262): the Staging plist is renamed `GoogleService-Info-Staging.plist`
and every configuration excludes every plist but its own, so W-37 is no longer needed.

**D-2. The `E4-04` guards reject the spec's benchmark configuration as written.**
`FirebaseConfigurationTest.developmentConfigurationIsAllowedOnlyInTheReviewedLocations` asserts the exact
set of development configuration paths, and
`iosDeveloperTeamIsSuppliedByAnUntrackedLocalConfiguration` counts exactly three
`Firebase.xcconfig` base references. The spec expects `FirebaseConfigurationTest` to pass unchanged after
adding `androidApp/src/benchmark/google-services.json` (`E403-15`, expectation 4); it would fail. This is
not a blocker: `D-238` requires a new build type to update the guard's expected set in the same change.

**D-3. Spec anchors that cannot be executed as written.** See R-1 to R-3 and §4, W-15 and W-16:

## 2. Reconciling the `E4-03` Spec with What `E4-04` Delivered

The spec assumed `release` was the only release-like build type. `D-259` now names `staging` as the
measured configuration. The reconciliations below keep every owner answer of 2026-10-24 and only adapt
how they are executed. R-1 to R-4 change the text of the reserved ADRs, so the owner confirms them at the
`E4-03` intake, inside the decision they belong to.

**R-1 (inside `D-252` and `D-254`). The Android `benchmark` build type is derived from `staging`.**
`create("benchmark") { initWith(getByName("staging")); applicationIdSuffix = ".debug"; signingConfig =
signingConfigs.getByName("debug"); matchingFallbacks += listOf("release") }` (each property set
explicitly, so it does not depend on what `initWith` copies). Its declared delta from `staging` is
exactly: `<profileable android:shell="true"/>` and the exported `BenchmarkSeedActivity` in
`androidApp/src/benchmark/AndroidManifest.xml`, the seeding activity source, and the two per-source-set
files that the Google Services plugin and Kotlin source sets cannot inherit: a byte-identical
`src/benchmark/google-services.json` and the Play Integrity `AppCheckProvider.kt` (or a `srcDir` pointing
at `src/staging/java`, which avoids the copy). `FirebaseConfigurationTest`'s expected set and the
`.gitignore` negation list gain the benchmark file in the same commit (D-2). Recorded figures are labelled
"`staging` (`D-259`), measured through its `benchmark` derivative (`D-252`)".
Rejected: measuring `staging` itself by seeding with `benchmark` and reinstalling `staging` over it; it
adds a reinstall to every run and drops `profileable`, which Macrobenchmark's trace capture relies on.

**R-2 (inside `D-253` and `D-254`). The iOS `Benchmark` configuration reuses the `Staging` mechanism, with
no `#if DEBUG` path.** This answers the brief's stop condition: reuse is possible.
- `configs:` gains `Benchmark: release` in the existing block.
- `carApp` `configFiles` gains `Benchmark: Config/Staging/Firebase.xcconfig` (the development reversed
  client ID with release semantics); `settings.configs.Benchmark` sets
  `PRODUCT_BUNDLE_IDENTIFIER: com.ruizurraca.carapp.debug`, `KOTLIN_FRAMEWORK_BUILD_TYPE: release`,
  `SWIFT_ACTIVE_COMPILATION_CONDITIONS: $(inherited) CARAPP_BENCHMARK` and
  `EXCLUDED_SOURCE_FILE_NAMES: GoogleService-Info.plist`.
- `firebaseConfigurationResourceName` maps `"Benchmark"` with `"Debug"` and `"Staging"`; the `D-238`
  pre-build script's `case` gains `Benchmark` (today it fails with `unknown configuration`), and its plist
  path maps `Benchmark` to the Staging file (or to the Debug file after the D-1 fix).
- The Crashlytics symbol phase already skips every configuration except `Release`.
- The `FirebaseConfigurationTest` xcconfig count and configuration list are updated in the same commit.

**R-3 (inside `D-254`). Extend the launch-hook rule rather than rely on its blind spot.**
`SwiftDebugOnlyHookRule` treats `processInfo.arguments` as a launch read, and accepts it under
`CARAPP_BENCHMARK` only together with a guard proving that `CARAPP_BENCHMARK` is defined in the
`Benchmark` configuration and nowhere else. Failing fixtures first (`D-16`). The `docs/SECURITY.md`
paragraph "The client could be steered only in Debug through the launch environment" gains the benchmark
hook.

**R-4 (applies `D-259`; no new ID). Correct the measured-configuration wording everywhere it repeats.**
`docs/SPECIFICATION.md §11` and the matrix cold-start and smoothness rows say "the `staging` build type
(`D-259`), a release-optimized build"; the consumption row says "optimized Kotlin binaries (the JVM task
and the `iosArm64` `RELEASE` binaries of `D-80`)" instead of naming `staging` (C-3); the two
`docs/BACKLOG.md` passages are corrected; ADR-0210 gets an amendment note at `:35` and `:92` (as `D-258`
did for its closure sentence). The ADR of `D-255` states the consumption-row reading so that `D-259`'s
text and the matrix agree.

**R-5. Settings cancellation (`E403-06`).** Add one assertion to the existing
`SettingsStateHolderTest.closeCancelsTheHolderJob` (or one sibling test): the caller's parent `Job`
stays active after `close()`. Do not create `SettingsStateHolderCancellationTest.kt`.

**R-6. Leak detection covers all 24 Compose instrumented classes.** The guard of `E403-26` already
walks every class; `E403-27`'s edit applies to the 24 classes, with `leakDetecting(...)` outermost
around the existing `RuleChain` of `SpanishDialogLocaleTest`.

**R-7. Record keeping.** Insert the `D-251` to `D-256` rows in numeric order (between `D-250` and
`D-257`) in all four mirrors; `contractCheck` does not check order, but readers do. Write "fifteen
required checks" wherever the spec says "ten" (C-7).
