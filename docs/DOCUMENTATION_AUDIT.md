# Documentation Audit - carApp MVP

> **Purpose.** Structured findings from a Senior KMP Architecture review of the definition package (`AGENTS.md`, `docs/SPECIFICATION.md`, `docs/CONTRACTS.md`, `docs/TECHNICAL_PLAN.md`, `docs/DECISION_BOARD.md`, `docs/BACKLOG.md`, `docs/SECURITY.md`, `docs/identifiers.md`, `docs/versions-matrix.md`, `docs/CONTRIBUTING.md`, `docs/templates/agent-handoff.md`).
>
> **Authority.** This document is **non-normative**: it is a working audit, not a source of rules. When a finding is accepted by the owner it MUST be folded into the appropriate normative document in the same change; the corresponding entry MUST be appended to `docs/PROJECT_LOG.md`. Findings are referenced by their short ID (`AUDIT-NN`) so that project-log entries and PRs can cite a single stable identifier.
>
> **Status legend.** `[Blocking]` indicates a finding that, if unresolved, would let two competent agents produce incompatible implementations. `[Drift]` indicates a finding where a normative and a derived document disagree, the derived document wins or is silent, and the normative wording is the implementation contract. `[Guardrail]` indicates an under-specified rule that needs a precise definition to be executable. `[Cosmetic]` indicates a finding that does not block implementation but should be cleaned up in the same change.
>
> **Critical domains reviewed.** KMP module architecture and dependency graph; data modelling (entities, scaled values, JSON/Firestore schemas, persistence DDL); workflows, state management, sync and concurrency; error taxonomy, logging, exception handling; API contracts (Swift-facing ABI, state holders, use cases, repositories, integrations).
>
> **Findings summary.** 56 findings: 21 blocking, 22 guardrails, 8 drift, 5 cosmetic.

An iOS engineer will treat `litersScaled` as a count, not as litres × 1000. The contract explains the scale in `§2`, but the Swift-facing name does not remind the consumer. | Either rename the Swift-facing fields with explicit unit suffixes (`litersScaled`, `totalCostMinor`, `odometerKm`, `dateEpochMillis` are fine because the suffixes already convey scale) and add a `README.md` section in `:shared` documenting the scaling factors, OR introduce plain Swift `typealias` wrappers (`Millilitres`, `MinorUnits`, `Kilometres`, `EpochMilliseconds`, `LitresPerHundredKmScaled`) in `iosApp` that name the scale explicitly. Pick one and document the choice. |

State-holder intent functions in `§20.10` (`setName(value: String)`, `setInitialOdometerKm(value: Long)`, etc.) all declare single parameters with no defaults, which is consistent. The reason `SwiftAppGraph` itself takes no parameters is implied but never stated. | Add to `§15.3`: `SwiftAppGraph` MUST expose a no-argument constructor; the `isDebugBuild` flag is consumed by the factory `createSwiftAppGraph` and applied during graph construction. | `CONTRACTS.md §11.6` — `CrashReporter` from Phase 0 `[Guardrail]` | `E0-08` adds `:core:analytics` to Phase 0. The contract says `CrashReporter` is required from Phase 0. None of `E0-03`, `E0-08` or `E0-04` enumerates this exact Phase 0 module set; an agent could ship Phase 0 with `core:auth` already wired, which violates `feature data` MUST NOT depend on `:core:auth`. | Add a Phase 0 module-set list to `BACKLOG.md` and assert it from `E0-04`. Phase 0 ships only `:core:model`, `:core:common`, `:core:analytics`, `:core:crash`, `:core:testing`. `:core:auth`, `:core:database`, `:core:sync` are Phase 1/2/3. |

## 2. Data Modeling

### 2.1 Identifiers, money and scaled values

| Reference (Location) | Detected Ambiguity / Inconsistency | Proposed Guardrail Definition (The Solution) |
| :--- | :--- | :--- |
| `CONTRACTS.md §20.0` — `EntityId`, `OwnerId`, `CurrencyCode` as `value class` wrapping `String` `[Blocking]` | The contract says value classes MUST NOT appear on the Swift-facing surface (`§15.3`). But `FuelEntryListItemUi.id`, `VehicleListItemUi.id`, `FuelEntryFormUiState.vehicleId`, etc. are typed as `String` on the Swift side while their domain counterparts (`FuelEntry.id`, `Vehicle.id`) are typed `EntityId`. There is no contract that fixes the canonical lower-case form for UUID v4 strings on the Swift side. | Add a sentence to `§20.10`: Swift-facing `id` fields are the lowercase canonical UUID v4 `String`. The Kotlin→Swift conversion is a contract: `EntityId.value` is exactly the field, lowercase. Add a Swift-side test asserting that an example UUID is rendered lowercase. |
| `CONTRACTS.md §2` "Time" — `kotlinx.datetime.Instant` `[Blocking]` | The contract requires `kotlinx-datetime`'s `Instant`, and `versions-matrix.md` says "Record the exact fully-qualified `Instant` package here, because recent versions relocate it." As long as `versions-matrix.md` is `TBD`, no agent can implement time types. The contract-check (`§18`) allowlist names the "pinned datetime type `kotlinx.datetime.Instant`" — if the pinned package is `kotlin.time.Instant` or some other relocation, the allowlist becomes wrong silently. | Pin `kotlinx-datetime` in `versions-matrix.md` as part of `E0-06`, with the exact package path (`kotlinx.datetime.Instant`). Until then, `contract-check` MUST treat the `Instant` reference in §20 as a `TBD` placeholder and fail with a clear message. Add a unit test that imports the pinned package at build time. |
| `CONTRACTS.md §2` `Money` data class — `minorUnits: Long` `[Blocking]` | The contract pins `Money` to `(minorUnits: Long, currency: CurrencyCode)`. `FuelEntry.totalCostMinor` is `Long`. `MinorUnits.factorFor` returns `Int?` per `§20.3`. The monetary arithmetic in `§2` multiplies by `minorUnitFactor` (`Int`) and divides by `1_000_000` (`Int`). The product `litersScaled * pricePerLiterScaled * minorUnitFactor` is at most `5·10^5 * 10^6 * 100 = 5·10^13`, which overflows 32-bit `Int` (max `2.1·10^9`). The contract does not explicitly say every arithmetic step is performed in `Long`, only the final results. | Add to `§2`: every intermediate step of the canonical monetary arithmetic is `Long`. The Kotlin implementation MUST NOT narrow to `Int`. Add a golden test that exercises the upper boundary values: `litersScaled = 500_000`, `pricePerLiterScaled = 999_999`, `minorUnitFactor = 100`. The intermediate value is `500_000 * 999_999 * 100 = 4.99·10^13`, which must not overflow. |
| `CONTRACTS.md §2` — `Float`/`Double` forbidden for consumption `[Guardrail]` | The rule says no `Float` or `Double` in money, volume, price and consumption calculations, "in every layer". But the Swift-facing types expose `consumptionAverageScaled: Long?` and `consumptionScaled: Long?` — SwiftUI will format these as `Double`/`CGFloat` for display. The rule is unambiguous for arithmetic but ambiguous for display-time conversions. | Add to `§2`: display-time conversion in SwiftUI or Compose is not arithmetic and is not covered by the `Float`/`Double` ban. The rule applies to storage, transport and any computation that derives a stored value. Add a Konsist rule that bans `Float`/`Double` types in `:core:*`, `:feature:*` and `:shared` source sets (with explicit allowlists for SwiftUI/Compose display code on the platform side). |
| `CONTRACTS.md §20.0.1` — `SUPPORTED_CURRENCY_CODES` set `[Guardrail]` | The set includes 21 ISO-4217 codes. The contract says every supported code has two decimal minor units, factor `100`. The list contains `HUF` (Hungarian forint), which historically had two decimals but some references still cite zero-decimal variants. The same applies to several other currencies on different dates. | Add to `§20.0.1`: every code in `SUPPORTED_CURRENCY_CODES` MUST be verified as two-decimal by the MVP locale defaults (Android and iOS `Locale` and `NSLocale`). If the runtime reports a different minor-unit factor for any of these codes, the validation falls back to `EUR`. Add a unit test using JVM and native `java.util.Currency` / `NSLocale` that asserts every supported code has minor digits = 2. |
| `CONTRACTS.md §3` "Domain model vs local row vs remote document" table — `deleted` row `[Drift]` | The table says `deleted` is stored, with the invariant `deleted == (deletedAt != null)` enforced by a `CHECK` constraint. The local row DDL in `TECHNICAL_PLAN.md §6` does not show the `CHECK` constraint explicitly; it says the `outbox` table has a `CHECK(entityType IN (...))` but the entity tables only mention the constraint textually. | Add the exact `CHECK` constraint DDL to `TECHNICAL_PLAN.md §6`: `CHECK((deleted = 0 AND deletedAt IS NULL) OR (deleted = 1 AND deletedAt IS NOT NULL))`. Add a migration test that asserts the constraint fires on a violating insert. |
| `CONTRACTS.md §3.1` `odometerInconsistent` recompute set — "Update that cannot affect chronological order" `[Blocking]` | The rule distinguishes updates that can affect order (`vehicleId`, `date`, `createdAt`, `id`, `odometerKm`) from updates that cannot. But `currency`, `litersScaled`, `pricePerLiterScaled`, `totalCostMinor`, `notes`, `isFullTank`, `hasMissedEntries` are not listed as order-affecting. Changing `date` to an earlier value moves the entry; changing `currency` does not. The contract correctly says "the updated row only if its stored `odometerInconsistent` could change; otherwise no odometer-inconsistency recompute is required." That wording is ambiguous: how does an agent know `odometerInconsistent` could change? The two values that govern it are the previous entry's odometer and the updated entry's odometer; only `odometerKm` itself affects the comparison. | Rewrite the rule to: "An update that does not modify `vehicleId`, `date`, `createdAt`, `id` or `odometerKm` does not require any `odometerInconsistent` recompute, because the comparison values are unchanged." Drop the ambiguous phrase "could change". Add `E1-04` and `E1-06` fixtures proving no recompute on `notes`/`currency` edits. |
| `CONTRACTS.md §3.1` recompute set — "Vehicle-level fuel-entry cascade tombstone" `[Blocking]` | The cascade says "each successor after each tombstoned row, de-duplicated". The phrase "after each tombstoned row" is ambiguous: does it mean each successor in the old positions (one successor per tombstoned row, even when they coincide), or each unique successor in the union of old positions? The de-duplication key is `id`, but the wording can be read as "for each row, the next non-deleted row at the time of that row's deletion". | Rewrite to: "Vehicle cascade tombstone: the union of `successor` of each tombstoned row in its pre-cascade chronological position, de-duplicated by `id`. A successor that is itself being tombstoned is not added." Add an `E1-06` fixture that asserts the recompute set is correct for a 3-row vehicle cascade. |
| `CONTRACTS.md §4` ordering rules `[Guardrail]` | The chronological order is `date ASC, createdAt ASC, id ASC`. The consumption calculation order is `odometerKm ASC, date ASC, id ASC`. The two orders differ. An agent implementing `observeFuelEntries` (which returns rows in some order) might use one order for the list and the other for consumption, producing inconsistent `currentOdometerKm`. | Add a sentence to `§4`: `observeFuelEntries` returns rows in **chronological** order, not calculation order. The repository's `observeConsumption` is responsible for sorting in calculation order. Add a contract-check or a Konsist fixture asserting the ordering comment of every `ORDER BY` in `:core:database` is annotated with the right order name. |
| `CONTRACTS.md §3.1` — "Updated row in its new position, its old successor before the update, and its new successor after the update" `[Blocking]` | This rule says the recompute set on an order-affecting update is `{ updatedRow, oldSuccessor, newSuccessor }`. If `oldSuccessor == newSuccessor`, the set collapses to `{ updatedRow, successor }`. The wording "its old successor before the update, and its new successor after the update" is ambiguous: are old and new successors distinct, or can they coincide? | Rewrite to: "Updated row, plus its pre-update successor (the next non-deleted entry in chronological order before the update), plus its post-update successor (the next non-deleted entry in chronological order after the update). If pre- and post-successors coincide, the row is included once." |
| `CONTRACTS.md §3.1` — "Tombstone: successor after the deleted row in the old chronological position" `[Blocking]` | "Old chronological position" is the row's position **before** the tombstone. A subsequent tombstone could shift successors further. The contract does not explicitly say whether the recompute set for a single tombstone includes only the successor in the row's pre-tombstone position or the chain of successors after each subsequent tombstone. | Rewrite to: "Tombstone: the successor of the deleted row in its pre-delete chronological position. Subsequent tombstones or edits recompute independently." Add an `E1-06` fixture proving the cascade case. |
| `CONTRACTS.md §20.5` — `UpdateSettingsCommand` `[Drift]` | The contract says `currency: CurrencyCode?` and `analyticsEnabled: Boolean?` where `null` means "unchanged". But `SettingsRepository.updateSettings` (`§12`) is a single-write operation: a `null` value is a partial update; both nulls is a no-op. There is no error for "no-op update" or for "both nulls" — the contract is silent. | Add: `updateSettings` returns `Outcome<Unit, AppError>`; an update with both fields `null` returns `Err(ValidationError.NoOp)` and mutates nothing. Add an `E1-10` test fixture. |

### 2.2 Local persistence DDL and outbox

| Reference (Location) | Detected Ambiguity / Inconsistency | Proposed Guardrail Definition (The Solution) |
| :--- | :--- | :--- |
| `TECHNICAL_PLAN.md §6` `outbox` DDL — `lastError TEXT` `[Guardrail]` | The contract says `lastError` and `lastErrorCode` columns exist, but `CONTRACTS.md §6` says "Retry and poison decisions are made on `code`, never on a message string." Storing `lastError TEXT` invites agents to use the text in logic; it should be a debug-only column. | Add to `TECHNICAL_PLAN.md §6`: `lastError TEXT` is a debug-only column for UI display and is **never** read by the sync engine. ### 2.3 Remote document schemas

| Reference (Location) | Detected Ambiguity / Inconsistency | Proposed Guardrail Definition (The Solution) |
| :--- | :--- | :--- |
| `CONTRACTS.md §16` allowed remote keys — `notes`, `brand`, `model` "Yes / Null, or string length 1..40 after repository normalisation" `[Guardrail]` | The contract marks nullable text fields as "Yes" (required) with a null-allowed value. A reader might infer that the key MUST be present in every remote document even when `null`. The `validPayload()` Firestore rule has to encode that distinction. | Rewrite the "Yes" column header for nullable fields as "Yes (nullable)". State explicitly: nullable fields MUST appear with a `null` value in every remote document. The `hasAll([...])` check requires the key to be present; nullability is checked separately. Add an `E3-01` emulator test that submits a document with `brand: null` and one with `brand` absent, and asserts the first passes while the second is rejected. |
| `CONTRACTS.md §16` `schemaVersion` exact value `1` `[Guardrail]` | The contract says `schemaVersion` is exactly `1` for the MVP. The remote rule says `request.resource.data.schemaVersion == 1`. But `§9.5` defines `UnsupportedSchemaVersion` as `schemaVersion > CLIENT_MAX_SCHEMA_VERSION`. ## 8. Summary

This audit identifies **56 findings**: 21 blocking (would let two competent agents diverge), 22 guardrails (under-specified rules that need precise definitions to be executable), 8 drifts (normative vs derived disagreements), and 5 cosmetic.

**Highest-priority blocking findings:**

1. `Ktor` and `Coil` placement vs `D-11` / `D-12` (`CONTRACTS.md §15.4`, `§15.5`).
2. `expect`/`actual` double-path with injected dependencies (`CONTRACTS.md §15.1`).
3. `SyncStatus` shape on the Swift ABI (`CONTRACTS.md §15.3`).
4. `validPayload()` Firestore rule not declared (`CONTRACTS.md §16`).
5. Outbox coalescing `ON CONFLICT` clause missing (`CONTRACTS.md §8`).
6. `odometerInconsistent` recompute set ambiguous on order-affecting vs non-order-affecting updates (`CONTRACTS.md §3.1`).
7. `CalculateConsumption` signature has unused parameters (`CONTRACTS.md §13`).
8. Adoption resets non-`SYNCED` state but does not state this (`CONTRACTS.md §11.4`).
9. `Money` overflow on boundary arithmetic (`CONTRACTS.md §2`).
10. Account deletion precondition not stated as a hard step (`CONTRACTS.md §11.5`).

**Recommended next step:** convert the **21 blocking findings** into ADR-sized change requests. Each finding should become one pull request that updates the normative document, adds a fixture or test in the corresponding backlog story, and appends an entry to `docs/PROJECT_LOG.md` with the `AUDIT-NN` ID. Findings should not be folded in batches because each is a single-rule change that needs review.
