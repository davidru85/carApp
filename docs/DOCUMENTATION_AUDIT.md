# Documentation Audit - carApp MVP

> **Purpose.** Structured findings from a Senior KMP Architecture review of the definition package (`AGENTS.md`, `docs/SPECIFICATION.md`, `docs/CONTRACTS.md`, `docs/TECHNICAL_PLAN.md`, `docs/DECISION_BOARD.md`, `docs/BACKLOG.md`, `docs/SECURITY.md`, `docs/identifiers.md`, `docs/versions-matrix.md`, `docs/CONTRIBUTING.md`, `docs/templates/agent-handoff.md`).
>
> **Authority.** This document is **non-normative**: it is a working audit, not a source of rules. When a finding is accepted by the owner it MUST be folded into the appropriate normative document in the same change; the corresponding entry MUST be appended to `docs/PROJECT_LOG.md`. Findings are referenced by their short ID (`AUDIT-NN`) so that project-log entries and PRs can cite a single stable identifier.
>
> **Status legend.** `[Blocking]` indicates a finding that, if unresolved, would let two competent agents produce incompatible implementations. `[Drift]` indicates a finding where a normative and a derived document disagree, the derived document wins or is silent, and the normative wording is the implementation contract. `[Guardrail]` indicates an under-specified rule that needs a precise definition to be executable. `[Cosmetic]` indicates a finding that does not block implementation but should be cleaned up in the same change.
>
> **Critical domains reviewed.** KMP module architecture and dependency graph; data modelling (entities, scaled values, JSON/Firestore schemas, persistence DDL); workflows, state management, sync and concurrency; error taxonomy, logging, exception handling; API contracts (Swift-facing ABI, state holders, use cases, repositories, integrations).
>
> **Findings summary.** 20 findings: 5 blocking, 13 guardrails, 1 drift, 1 cosmetic.

Any Room type appearing in a `:core:*` signature would therefore be flagged as undeclared, or silently accepted if the parser is lenient. | Extend the `§18` ignored-identifier set with an explicit "Room-generated types" category: `AppDatabase`, Room `Dao` supertypes, and `@Entity`-generated classes that live in `:core:database`. The necessity of the `:core:sync -> :core:auth` edge is therefore unstated. | Either (a) justify the edge: state in `§10` or `§7` that `:core:sync` calls `TokenProvider.getIdToken` directly on the `AuthExpired` retry path, and document the call; or (b) remove `:core:auth` from `:core:sync`'s allowed list, leaving token handling entirely to `:integration:firebase-firestore` via `RemoteSyncSource`. Exposing them to Swift invites the iOS layer to fire system triggers manually, duplicating `BGTaskScheduler` wiring and bypassing the single-`SyncController` invariant of `§9.1`. | Add to `§20.10`: `SyncStateHolder.requestSync` is intended for user-initiated sync only; the Swift-facing surface MUST pass `SyncTrigger.PullToRefresh` (and `AppForeground` if the platform emits it from a lifecycle hook). `PostWriteDebounce`, `ConnectivityRecovered` and `Periodic` are fired exclusively by `SyncTriggerAdapter` from platform wiring and MUST NOT be invoked from Swift UI code. Add a Konsist fixture banning those three leaves from any `iosMain` call site. |

| `CONTRACTS.md §20.7` `SyncStatus` (sealed class) vs `§20.9` `SyncStatusCategory` (enum) `[Guardrail]` | `SyncStatus` is a `sealed class` with `Idle`, `Syncing`, `Pending(count)`, `Failed(retryableCount, poisonedCount)`. `SyncStatusCategory` is a flat `enum { IDLE, SYNCING, PENDING, FAILED }` used by `AnalyticsEvent.SyncStatusChanged(status)`. ### 2.1 Local persistence DDL

| Reference (Location) | Detected Ambiguity / Inconsistency | Proposed Guardrail Definition (The Solution) |
| :--- | :--- | :--- |
| `TECHNICAL_PLAN.md §6` — `sync_cursor` table DDL `[Guardrail]` | `§6` lists `sync_cursor` as a table and `SPECIFICATION.md §9.2` names its columns (`entityType`, `lastServerUpdatedAt`, `lastDocumentId`), but no DDL with column types, nullability, primary key, or `entityType` CHECK constraint is provided. Compare with `outbox` and `quarantine`, which both have full DDL. An agent implementing `E1-01` would have to invent the column types. | Add the exact DDL to `TECHNICAL_PLAN.md §6`: `CREATE TABLE sync_cursor (entityType TEXT NOT NULL CHECK (entityType IN ('VEHICLE','FUEL_ENTRY')), lastServerUpdatedAt INTEGER NOT NULL, lastDocumentId TEXT NOT NULL, PRIMARY KEY (entityType))`. Note `lastDocumentId` is `TEXT NOT NULL` because `§9.4` forbids `null` as a cursor component; the `INITIAL` cursor is a sentinel, not a stored row. Add an `E1-01` migration test. |
| `TECHNICAL_PLAN.md §6` `quarantine` DDL — `reason TEXT` `[Guardrail]` | The DDL stores `reason TEXT NOT NULL` but `QuarantineReason` (`§20.7`) is a closed enum with two leaves. There is no `CHECK (reason IN (...))` constraint, unlike `outbox.entityType` which has one. An agent could persist an arbitrary reason string. | Add `CHECK (reason IN ('UnsupportedSchemaVersion','MalformedPayload'))` to the `quarantine` DDL in `§6`. Add an `E3-03` migration test proving the constraint rejects an unknown reason. |
| `CONTRACTS.md §17` — `cycleId` storage in `outbox.lastError` context `[Guardrail]` | `§17` says every sync cycle generates a `cycleId` that "is included as a field on every sync log line and stored in `outbox.lastError` context." `§20.7` declares `CycleId` as a value class. But the `outbox` DDL (`TECHNICAL_PLAN.md §6`) has only `lastError TEXT` and `lastErrorCode TEXT`; there is no `cycleId` column, and the serialization format of the "context" inside `lastError` is undefined. `§9.7` also says `lastError` is debug/UI-only and MUST NOT be read by the sync engine, so the engine cannot rely on parsing `cycleId` out of it. | Either (a) add a `cycleId TEXT` column to the `outbox` DDL, populated on every failed attempt, and state that the sync engine reads it only for logging correlation; or (b) clarify in `§17` that `cycleId` is carried in log fields only, not in the `outbox` row, and remove the "stored in `outbox.lastError` context" wording. Pick one and update `§6`, `§17` and `E3-03` consistently. |
| `CONTRACTS.md §20.7` `RemoteCursor.INITIAL` vs `§9.4` "null MUST NOT be used as a cursor component" `[Guardrail]` | `RemoteCursor.INITIAL = RemoteCursor(Instant.fromEpochMilliseconds(0), null)` has `lastDocumentId = null`. `§9.4` states "`null` MUST NOT be used as a cursor component." The `INITIAL` cursor is a sentinel that triggers the `startAt(overlapSince, "")` path and is never passed directly to Firestore, but a literal reading makes `INITIAL` illegal. An agent could "fix" `INITIAL` by setting `lastDocumentId = ""`, which would then be passed to `startAfter` on a resumed cycle and produce wrong pagination. | Add to `§20.7`: `RemoteCursor.INITIAL` is a sentinel representing "no cursor stored yet"; it is never passed to `RemoteSyncSource.pullChanges`. The sync engine materialises the first page cursor as `(overlapSince, "")` per `§9.4`. Add to `§9.4`: the `null` prohibition applies to cursors passed to `startAt`/`startAfter`; the `INITIAL` sentinel is exempt because it is translated before reaching Firestore. Add an `E3-03` test proving `INITIAL` never reaches `RemoteSyncSource`. |

| `CONTRACTS.md §20.10` `SessionStateHolder` — no intent for anonymous conversion (F-4) `[Blocking]` | `SessionStateHolder` exposes `startAnonymousSignIn`, `startPermanentSignIn(provider)`, `requestSignOut`, `confirmSignOut`, `requestDeleteAccount`, `confirmDeleteAccount`. `SPECIFICATION.md §7 F-4` (Anonymous Account Conversion) is a distinct flow: from settings, the user links Google or Apple credentials to the current anonymous identity. | `CONTRACTS.md §20.10` `SessionPhase` — `LOCAL -> DELETING` semantics `[Guardrail]` | The normative `SessionPhase` transition table allows `LOCAL -> DELETING`. For a `LOCAL_OWNER` session there is no Firebase Auth account, so the `D-23` server account-deletion operation cannot run. `SPECIFICATION.md §7 F-5` says the anonymous equivalent is "delete local data", which clears local tables but performs no remote purge. The `DELETING` phase therefore means two different things depending on the starting phase: server account deletion (from `ANONYMOUS`/`PERMANENT`) vs. local-data clear (from `LOCAL`). The contract does not distinguish them. | Add to `§20.10`: from `LOCAL`, `DELETING` means "clearing local data only" (no server operation); from `ANONYMOUS`/`PERMANENT`, `DELETING` means "running the `D-23` server operation then clearing local data". State that the `DELETING -> UNKNOWN` transition is followed by `UNKNOWN -> SIGNED_OUT` only after the local-data clear completes. Update `E2-05` to test both paths. |
| `CONTRACTS.md §20.8` `AuthToken(val value: String, expiresAt: Instant)` vs `§11.5` "fresh" token `[Guardrail]` | `§11.5` says the app MUST verify the Firebase ID token is fresh, "meaning younger than `FRESH_LOGIN_THRESHOLD_MS`". `AuthToken` carries `expiresAt` but no `issuedAt`. "Younger than 5 minutes" is a statement about issuance age, not expiry. An agent cannot compute issuance age from `expiresAt` alone (Firebase tokens have a 1-hour validity, so `expiresAt - 5 min` approximates issuance, but the contract does not state this). The relationship between `expiresAt`, `FRESH_LOGIN_THRESHOLD_MS` and the freshness check is undefined. | Add to `§20.8` either an `issuedAt: Instant` field on `AuthToken` (populated by `TokenProvider`) or a normative rule in `§11.5`: freshness is computed as `AppClock.now() - (expiresAt - FIREBASE_TOKEN_VALIDITY) > FRESH_LOGIN_THRESHOLD_MS` is false, where `FIREBASE_TOKEN_VALIDITY` is a pinned constant. Prefer `issuedAt` for explicitness. Update `E2-02` and `E2-05` to test the freshness check. |

### 4.1 Error-to-analytics mapping

| Reference (Location) | Detected Ambiguity / Inconsistency | Proposed Guardrail Definition (The Solution) |
| :--- | :--- | :--- |
| `CONTRACTS.md §20.9` `ConversionFailureReason` / `DeletionFailureReason` vs `§20.2` `AuthError` `[Guardrail]` | `AnalyticsEvent.AccountConversionFailed(reason: ConversionFailureReason)` and `AccountDeletionFailed(reason: DeletionFailureReason)` use analytics-specific bucket enums. `AuthError` has the operational leaves `Cancelled`, `CredentialAlreadyInUse`, `NetworkUnavailable`, `UidWouldChange`, `PermissionDenied`, `RequiresRecentLogin`, `AccountDeletionRemoteFailed`, `Unknown`. | `CONTRACTS.md §16.1` — failure analytics events vs "track after successful use case results" `[Guardrail]` | `§16.1` says "Shared presentation or application-level orchestration may track product events **after successful use case results**." `AnalyticsEvent` includes `AccountConversionFailed`, `AccountDeletionFailed` and `SyncStatusChanged` — these are failure/state events, not success events. The rule contradicts the existence of failure leaves. An agent could either omit failure tracking (following the rule) or emit it (following the type), and neither is provably wrong from the docs. | Rewrite `§16.1`: "Shared presentation or application-level orchestration may track product events after a use case returns `Ok` **or** `Err`, provided the event payload carries no user data. An agent could report every `UnexpectedError` as a non-fatal, or never report anything. | Add to `§20.3.1` a trigger policy: `recordNonFatal` MUST be called for every `UnexpectedError` and for every `SyncError.Poisoned`/`FAILED_POISONED` transition; it MUST NOT be called for validation warnings, expected `AuthError` leaves, or connectivity-only `RemoteError` codes. `fields` follows the same allowlist as `Logger` (`§17`).
